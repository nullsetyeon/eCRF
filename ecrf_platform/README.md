# e-CRF 플랫폼 (범용 CRF 빌더 프로토타입)

비개발자인 연구자가 **웹 화면만으로** 임상연구 CRF(증례기록지)를 설계하고,
여러 연구원과 함께 데이터를 입력·관리할 수 있도록 만든 자체 개발 플랫폼입니다.
엑셀이나 코드 작성 없이 관리자 화면에서 문항을 추가/수정하면 바로 데이터 입력
화면이 생성됩니다.

> 이 문서는 조나현 선생님(대전대학교 천안 한방병원)의 "고혈압 생맥산가감방 연구"
> e-CRF 프로토타입 세션에서 이어진, **범용 플랫폼 버전**입니다. 특정 연구 1건이
> 아니라 여러 연구를 계속 새로 만들 수 있는 구조로 설계되었습니다.

## 핵심 기능

- **방문(Visit) 스케줄 설계**: V1, V2, V3... 처럼 연구 방문 일정을 자유롭게 정의
- **웹 화면 CRF 빌더**: 폼(증례기록지 페이지)마다 문항을 하나씩 추가/수정/삭제,
  드래그로 순서 변경 (Excel/코드 불필요)
- **문항 유형**: 단답형/장문형 텍스트, 숫자, 날짜, 라디오버튼, 드롭다운, 체크박스
  (다중선택), 자동 계산 필드, 섹션 구분선
- **분기 로직(Skip logic)**: "흡연 여부=예일 때만 흡연기간 문항 표시"처럼 특정
  응답에 따라 문항을 보이거나 숨김
- **자동 계산 필드**: 예) `BMI = round(weight / ((height/100) ** 2), 1)` 같은
  산술식을 다른 문항 값으로 자동 계산 (안전한 수식 평가기 사용, 임의 코드 실행 불가)
- **반복 입력 폼**: 이상반응 로그, 병용약물 로그처럼 여러 건을 반복 기록하는 폼 지원
- **연구별 권한 관리**: 플랫폼 관리자 / 연구 관리자(설계·초대 가능) / 연구원(입력·조회만)
- **감사추적(Audit trail)**: 로그인/로그아웃, 연구·방문·폼·문항 설계 변경, 대상자
  등록, 데이터 입력/수정, 데이터 내보내기까지 누가 언제 무엇을 했는지 기록
- **데이터 내보내기**: 연구 전체 데이터를 폼별 CSV로 묶은 ZIP 파일로 다운로드
  (엑셀에서 바로 열람 가능)

## 로컬에서 실행해보기

```bash
cd ecrf_platform
python3 -m venv .venv && source .venv/bin/activate   # (선택) 가상환경
pip install -r requirements.txt

cp .env.example .env
# .env 파일을 열어서 SECRET_KEY를 무작위 문자열로 바꿔주세요.
# 생성 팁: python3 -c "import secrets; print(secrets.token_hex(32))"

export FLASK_APP=run.py
flask create-admin      # 이름/이메일/비밀번호를 입력해서 최초 관리자 계정 생성
python3 run.py           # http://localhost:5000 접속
```

첫 로그인 후 순서: **연구 생성 → 방문 추가 → 폼 추가 → 문항 설계 → 연구원 초대
→ (연구원 화면에서) 대상자 등록 → 방문별 데이터 입력 → 데이터 내보내기**

## 자동 검증 (스모크 테스트)

리포지토리에 포함된 `smoke_test.py`는 위 전체 흐름(연구 생성부터 분기로직·자동계산
·반복입력폼·권한분리·CSV 내보내기·감사로그까지)을 자동으로 실행해서 검증합니다.

```bash
python3 smoke_test.py
```

기능을 수정한 뒤에는 이 스크립트를 다시 실행해서 회귀(regression)가 없는지
확인하는 것을 권장합니다.

## 인터넷 서버에 배포하기 (여러 연구자가 접속하려면 필수)

로컬 실행은 본인 컴퓨터에서만 접속되므로, 여러 연구자가 각자 브라우저로
접속하려면 인터넷에 호스팅해야 합니다. 비개발자·1인 운영 환경에는 서버를 직접
관리할 필요가 없는 **관리형 클라우드(PaaS)**를 추천합니다.

### 추천: Render.com (또는 Railway.app)

두 곳 모두 (1) GitHub 저장소만 연결하면 자동 배포, (2) HTTPS 자동 적용,
(3) 관리형 PostgreSQL 제공, (4) 무료/저가 요금제 존재 라는 공통점이 있어
서버 운영 경험이 없어도 시작하기 쉽습니다. 아래는 Render 기준 절차입니다.

1. 이 폴더를 GitHub 저장소로 올립니다 (`.env`는 `.gitignore`에 포함되어
   있으므로 절대 커밋되지 않습니다 — 비밀키가 깃허브에 노출되지 않도록 주의).
2. Render 대시보드 → **New → PostgreSQL** 로 데이터베이스를 하나 만듭니다.
3. Render 대시보드 → **New → Web Service** 로 방금 올린 GitHub 저장소를 연결합니다.
   - Build Command: `pip install -r requirements.txt`
   - Start Command: `gunicorn "app:create_app()"`
4. Web Service의 **Environment** 설정에서 아래 값을 등록합니다.
   - `SECRET_KEY`: 무작위 문자열 (로컬에서 만든 것과 다른 값 사용)
   - `DATABASE_URL`: 2번에서 만든 PostgreSQL의 Internal Connection String
   - `SESSION_COOKIE_SECURE`: `1`
5. 배포가 끝나면 Render Shell(또는 `render-cli`)에서 한 번만 실행:
   ```bash
   flask create-admin
   ```
   (또는 로컬에서 `DATABASE_URL`을 운영 DB로 임시 지정하고 실행해도 됩니다.)
6. 발급된 `https://xxxx.onrender.com` 주소를 연구원들에게 공유하면 각자
   브라우저로 접속해 로그인할 수 있습니다.

Railway.app도 절차가 거의 동일합니다 (PostgreSQL 플러그인 추가 → 저장소 연결 →
환경변수 등록 → 배포).

## 보안 수준에 대한 안내 (중요)

임상연구 데이터는 개인정보·건강정보를 포함하므로 보안이 중요합니다. 이번
프로토타입(MVP)에는 아래 **기본 보안 기능**이 구현되어 있습니다.

- 비밀번호 해시 저장 (평문 저장 안 함)
- 세션 기반 로그인, 30분 미사용 시 자동 로그아웃
- 연구별 접근권한 분리 (플랫폼 관리자 / 연구 관리자 / 연구원)
- 모든 폼 제출에 CSRF(위조 요청 방지) 토큰 적용
- 운영 배포 시 HTTPS 쿠키 강제(`SESSION_COOKIE_SECURE`) 옵션
- 기본 보안 헤더(X-Frame-Options, X-Content-Type-Options 등)
- **감사추적(Audit trail)**: 누가/언제/무엇을 변경했는지 전부 기록 (`audit_logs`
  테이블) — 다만 이번 버전은 "변경 이력 기록"까지만 구현했고, 전자서명(e-signature)
  이나 필드 단위 이전 값 비교, 데이터 잠금(lock) 같은 임상시험 규제 수준
  (21 CFR Part 11 등)의 기능은 아직 없습니다. 필요해지면 다음 단계로 추가할 수
  있는 구조로 설계했습니다 (AuditLog 테이블에 이미 사용자·시각·행위가 남고 있음).

**아직 구현되지 않은 것 / 운영 전 반드시 점검할 것**

- 대상자 식별정보: 실명 대신 등록번호(예: HP-001)만 저장하도록 설계했습니다.
  실명·주민번호 등 직접식별정보는 이 시스템에 입력하지 않는 것을 권장합니다.
- 데이터베이스 암호화, 정기 백업 정책은 별도로 구성해야 합니다 (Render/Railway의
  관리형 PostgreSQL은 기본 백업을 제공하지만, 보존기간·복구 절차를 확인하세요).
- 비밀번호 정책(최소 길이/복잡도 강제), 2단계 인증은 아직 없습니다.
- **이 프로토타입을 실제 IRB 승인 연구의 정식 데이터 수집 도구로 쓰려면, 해당
  연구계획서에 명시된 데이터 수집 방법(예: 기존 Mytrial e-CRF)과 다르므로
  IRB/연구계획서 변경 승인을 먼저 받아야 할 수 있습니다.**

## 데이터 모델 요약

`Study`(연구) → `Visit`(방문 스케줄) → `FormTemplate`(폼) → `Field`(문항) 순으로
설계 정보를 정의하고, `Subject`(대상자) → `VisitInstance`(실제 방문 1회) →
`ResponseRecord`(폼 제출 1건) → `ResponseValue`(문항별 응답값) 순으로 실제
데이터가 쌓입니다. 모든 변경은 `AuditLog`에 기록됩니다. 자세한 필드는
`app/models/` 폴더를 참고하세요.
